# 04 性能优化与运维

> English version: [04_performance_and_ops.md](../en/50_deployment/04_performance_and_ops.md)

## 目标

- 学会用 htop/iotop + `rostopic hz/delay` 判断瓶颈在算力还是传输，并按模块查表降载。
- 掌握 CPU 绑核、日志治理、远程运维（远程 rviz、rosbag 黑匣子）与 EOL 下的升级策略。

## 背景

边缘单元的算力是固定预算：3D SLAM、导航、传感器驱动同时跑，CPU 打满的直接症状是话题掉频、TF 超时、导航抖动。运维的第一步不是调参而是**定位瓶颈**——先分清"算不过来"还是"传不过来"，再对症下药。

## 第一步：资源监控与瓶颈定位

```bash
sudo apt install -y htop iotop
htop          # 按核看 CPU；F6 按 CPU% 排序找大户（常见: slam 节点、move_base、rviz）
sudo iotop -o # 只显示有 IO 的进程；rosbag record / rosout 写盘大户在这现形
df -h /       # 磁盘水位，长期运行必查
```

ROS 侧两把尺子：

```bash
rostopic hz /scan            # 实际频率 vs 标称频率
rostopic delay /scan         # 消息头时间戳到收到的延迟（需消息带 header）
```

判读方法：

| 现象 | 结论 | 方向 |
| --- | --- | --- |
| 发布端 hz 就低，CPU 某核打满 | **算力瓶颈**：节点算不完 | 降载（下表）、绑核 |
| 发布端 hz 正常，订阅端 hz 低 / delay 大 | **传输瓶颈**：带宽或跨机网络 | 降采样、压缩传输、检查 WiFi |
| hz 正常、delay 周期性尖峰 | 调度抖动或时间没同步 | 绑核；多机先查 chrony（[01 节](01_实机部署清单.md)） |

跨机看图像/点云还可用 `rostopic bw <topic>` 估带宽，WiFi 环境点云轻松打满链路。

## 第二步：按模块降载手段汇总表

各章教过的参数，从"运维减负"角度汇总回扣：

| 模块 | 降载手段 | 参数/做法 | 详见 |
| --- | --- | --- | --- |
| costmap | 降分辨率、降更新频率、缩小 local 窗口 | `resolution: 0.05→0.1`、`update_frequency: 5→2`、`width/height` | [40 章 costmap 调参](../40_导航/02_costmap代价地图调参.md) |
| gmapping | 减粒子数、降建图更新间隔 | `particles: 30→10`、`map_update_interval` 调大 | [20 章 gmapping](../20_2D建图/02_gmapping实战.md) |
| 3D SLAM | 加大体素滤波、降输出频率 | FAST-LIO `filter_size_surf/map` 调大；LIO-SAM 同理 | [25 章](../25_3D激光SLAM/README.md) |
| 点云 | 前置降采样再进算法 | `pcl_ros` VoxelGrid nodelet，`leaf_size: 0.1` | [25 章](../25_3D激光SLAM/01_3D激光SLAM概览与准备.md) |
| 可视化 | **实机不跑 rviz** | rviz 单进程能吃掉 1–2 个核：改远程 rviz（下文）或 web 方案（rosboard/foxglove） | 本节 |
| 局部规划 | 降采样数 | DWA `vx_samples`、TEB 视野/优化步数 | [40 章](../40_导航/03_DWA与TEB局部规划器.md) |

原则：先降"看的"（可视化、调试话题），再降"建的"（建图精度），最后才动"跑的"（控制频率不轻易降）。

## 第三步：CPU 绑核与实时性

把关键节点绑到独立核，避免与其他大户互相挤：

```bash
# 查 PID 后绑核（把 slam 绑到 2、3 核）
taskset -cp 2,3 $(pgrep -f fastlio_mapping)

# launch 里直接用 launch-prefix 固化
<node pkg="..." type="..." name="slam" launch-prefix="taskset -c 2,3"/>
```

系统级隔离可用 cgroup/cpuset 把系统杂务限制在 0、1 核，2 核以上留给 ROS——用 `systemd` 的 `CPUAffinity=`（写进 [02 节](02_systemd开机自启.md)的 service `[Service]` 段）最省事。

实时调度 `chrt -r`（SCHED_RR）**慎用**：ROS1 节点不是为硬实时写的，把吃满 CPU 的节点提成实时优先级可能饿死系统进程直至机器失联。一般机器人绑核 + `nice -n -5` 已够用。

## 第四步：日志运维

不治理日志，长期运行的机器一定爆盘。三处着手：

```bash
# 1. journald 上限（systemd 服务日志，02 节已提）
sudo sed -i 's/^#\?SystemMaxUse=.*/SystemMaxUse=500M/' /etc/systemd/journald.conf
sudo systemctl restart systemd-journald

# 2. rosout 文件日志: 每次 roslaunch 都在 ~/.ros/log 新建目录且从不清理
rosclean check    # 看当前占用
rosclean purge -y # 手动清空

# 3. cron 定期清理（保留 7 天），crontab -e 添加:
0 3 * * * find /home/iot/.ros/log -maxdepth 1 -mtime +7 -exec rm -rf {} +
```

> 以 root 跑的容器里日志在 `/root/.ros/log`，[03 节](03_Docker部署.md)已把它挂载到宿主机 volume，同样纳入上面的 cron。另可在 launch 里给吵闹节点降级：`<env name="ROSCONSOLE_MIN_SEVERITY" value="WARN"/>`。

## 第五步：远程运维

**远程 rviz**：实机 headless，不装/不跑 rviz。操作台设 `ROS_MASTER_URI` 指向实机（[01 节](01_实机部署清单.md)多机配置）后本地跑 rviz，渲染算力花在操作台。网络不通透时用 ssh 端口转发兜底：

```bash
ssh -L 11311:localhost:11311 iot@192.168.1.10   # 转发 master 端口
# 注意: ROS1 节点还会用随机端口，纯转发不完整；正道是打通网络 + ROS_IP，转发只用于应急看 master
```

**rosbag 黑匣子**：定时录制关键话题快照，出事后回放定位（回放方法见 [10 章 rosbag 篇](../10_ROS1基础/08_rosbag与调试工具.md)）：

```bash
# 每小时录 60 秒关键话题，配合 cron；--split --max-splits 控制总量
0 * * * * bash -lc 'source /opt/ros/noetic/setup.bash && rosbag record -O /home/iot/robot_data/bags/snap_$(date +\%H).bag --duration=60 /scan /odom /tf /rosout'
```

按小时命名自动覆盖前一天同时段文件，磁盘占用恒定。持续录制场景改用 `rosbag record --split --size=1024 --max-splits=10` 环形保留最近 10 GB。

**异常自愈**：节点崩溃重启已由 [02 节](02_systemd开机自启.md) `Restart=on-failure` 兜底，运维侧只需在 journalctl 里定期核对重启次数：`journalctl -u ros-robot | grep -c "Started ROS1"` 异常增大就该查原因了。

## 第六步：固件/系统升级策略（EOL 现实）

Noetic 与 Ubuntu 20.04 均已进入 EOL 周期，升级策略只有一个词：**冻结**。

- 裸机部署的机器：不做 `apt upgrade`（[01 节](01_实机部署清单.md)已关自动更新）。EOL 后升级收益趋零、风险常在（依赖被动了就再也装不回来）。
- 一切功能改动走 **Docker 镜像版本化**（[03 节](03_Docker部署.md)）：改代码 → 构建 `romindly/ros1-noetic:1.1` → 台架验证 → save/load 发放产线 → 有问题回滚到 `:1.0`。镜像 tag 就是发布版本号，宿主机永远不动。
- 确需安全补丁的联网设备，评估 Ubuntu Pro（20.04 ESM 延长维护）覆盖系统层，ROS 层继续冻结。

## 常见问题

- **CPU 不高但导航卡顿**：看 `rostopic delay /tf` 与 chrony——多机时间不同步的表象常被误判为性能问题。
- **rviz 一开机器人就变卡**：rviz 跑在实机上了，改远程 rviz；点云话题订阅本身也占实机带宽/CPU，调试完记得关。
- **磁盘几周后满**：三个嫌疑按序排查——`~/.ros/log`（rosclean）、journal（SystemMaxUse）、rosbag 目录（环形覆盖策略）。
- **绑核后更卡**：核给少了，节点内部多线程（如 move_base）被挤在两个核上。`htop` 按线程（H 键）确认线程数再分配。
- **想升级某个 ROS 包修 bug**：EOL 源里没有新版；从源码把该包放进工作空间 overlay 编译，并把改动固化进下一版 Docker 镜像。
