# 03 Docker Deployment

## Goal

Building on the quick reference in [docker/README.md](https://github.com/Romindly-Dev/romindly_ros1_workspace/blob/main/docker/README.md), walk through the full path: build the image → run with device/network/display access → distribute offline to the production line → container autostart on boot → data persistence → multi-container orchestration.

## Background: After EOL, Docker Is the Right Answer

ROS Noetic reached EOL in May 2025, which raises two practical problems: the apt repository no longer receives updates (the version combination you can install today may not be installable identically tomorrow after the official repository changes); and Ubuntu 20.04 itself is approaching the end of standard support. A bare-metal environment is "alive"—every installation is one of a kind, with no guarantee that machine #10 matches machine #1.

A Docker image turns the **entire dependency set into a read-only snapshot**: ROS, apt packages, and build artifacts are all frozen inside one image file. `docker build` once, and the environments produced by `docker load` on N production machines are byte-for-byte identical; upgrading = switching the image tag, rolling back = switching back to the old tag. This is exactly the right way to maintain an EOL system long-term (see [Section 04](04_performance_and_ops.md) for the upgrade strategy).

## Dockerfile Walkthrough, Section by Section

See [docker/Dockerfile](https://github.com/Romindly-Dev/romindly_ros1_workspace/blob/main/docker/Dockerfile) for the complete file:

```dockerfile
FROM ros:noetic-ros-base-focal
```

Based on the official OSRF image: Ubuntu 20.04 (focal) + ros-base (no GUI), with the ROS apt source and key already configured—**you will not hit the EXPKEYSIG problem inside the image**, because the key inside the image is updated along with the base image.

```dockerfile
RUN sed -i 's|http://archive.ubuntu.com|https://mirrors.tuna.tsinghua.edu.cn|g; ...' /etc/apt/sources.list
```

Switches to the Tsinghua mirror to speed up builds in China; comment it out for overseas deployments.

```dockerfile
RUN apt-get update && apt-get install -y --no-install-recommends \
    git vim wget curl python3-catkin-tools python3-vcstool python3-rosdep \
    ros-noetic-xacro ros-noetic-robot-state-publisher ... \
    && rm -rf /var/lib/apt/lists/*
```

One layer installs all the tools and ROS packages used by the tutorials. `--no-install-recommends` reduces size; deleting the apt cache at the end is a Docker convention (each RUN is a layer, and keeping the cache just wastes image size).

```dockerfile
WORKDIR /root/ws_romindly
COPY ros1.repos /root/ws_romindly/
RUN mkdir -p src && vcs import src < ros1.repos || true
RUN source /opt/ros/noetic/setup.bash && \
    apt-get update && rosdep install --from-paths src --ignore-src -r -y || true && \
    catkin_make || true && rm -rf /var/lib/apt/lists/*
```

At build time the repositories listed in `ros1.repos` are pulled into the image and compiled—**the code and build artifacts also go into the snapshot**. `|| true` keeps individual package failures from aborting the build (a lenient policy for a teaching image; for production images, remove it so failures are surfaced).

```dockerfile
RUN echo "source /opt/ros/noetic/setup.bash" >> /root/.bashrc && ...
CMD ["bash"]
```

Sources automatically when entering the container interactively; the default command is bash (production autostart overrides CMD—see below).

## Build and Run

```bash
cd ~/ws_romindly/src/romindly_ros1_workspace/docker
cp ../ros1.repos .
docker build -t romindly/ros1-noetic:1.0 .     # tag with a version number, not just latest
```

Expect the output to end with `Successfully tagged romindly/ros1-noetic:1.0`.

Three typical ways to run (they can be combined):

```bash
# 1. Network: --net=host shares the host network stack; ROS1 nodes use random ports, so host mode is mandatory
docker run -it --net=host romindly/ros1-noetic:1.0

# 2. Device passthrough: access the LiDAR / base serial port
docker run -it --net=host --privileged -v /dev:/dev romindly/ros1-noetic:1.0
# Verify inside the container: ls -l /dev/rplidar

# 3. Graphics (rviz): pass through X11
xhost +local:docker
docker run -it --net=host -e DISPLAY=$DISPLAY \
  -v /tmp/.X11-unix:/tmp/.X11-unix romindly/ros1-noetic:1.0
```

> `--privileged -v /dev:/dev` is crude but effective, with fully open permissions; the tightened variant is passing devices one by one with `--device=/dev/rplidar`, at the cost of restarting the container after hot-plugging. udev rules are configured on the **host** ([Chapter 45](../45_sensor_drivers/04_udev_and_device_management.md)); the symlinks seen inside the container are generated by the host.

## Image Distribution: Offline Import to the Production Line

Production machines often have no internet access; use save/load via a USB drive or the local network:

```bash
# Export on the development machine (gzip-compressed; the Noetic base image is about 1–2 GB after gzip)
docker save romindly/ros1-noetic:1.0 | gzip > romindly-ros1-1.0.tar.gz

# Import on the production machine
gunzip -c romindly-ros1-1.0.tar.gz | docker load
docker images    # should show romindly/ros1-noetic  1.0
```

Ship a `sha256sum` checksum file along with the package, and verify integrity before importing.

## Container Autostart on Boot: Two Approaches

| Approach | Method | Pros | Cons |
| --- | --- | --- | --- |
| Docker's built-in restart policy | `docker run -d --restart=always ...` | One command; the docker daemon pulls the container up as soon as it starts | Cannot express dependencies (waiting for devices/network); coarse start/stop granularity; cannot be orchestrated with other systemd services |
| systemd-managed container | Write a service whose ExecStart is `docker run` | Reuses all the capabilities of [Section 02](02_systemd_autostart.md): After/Requires, KillSignal, journalctl | One more file to maintain |

Approach 1:

```bash
docker run -d --name ros-robot --restart=always --net=host \
  --privileged -v /dev:/dev romindly/ros1-noetic:1.0 \
  bash -c "source /root/ws_romindly/devel/setup.bash && roslaunch robot_bringup robot.launch"
```

Approach 2 (recommended, consistent with the Section 02 setup), `/etc/systemd/system/ros-robot-docker.service`:

```ini
[Unit]
Description=ROS1 Robot (Docker)
After=docker.service network-online.target dev-rplidar.device
Requires=docker.service dev-rplidar.device

[Service]
ExecStartPre=-/usr/bin/docker rm -f ros-robot
ExecStart=/usr/bin/docker run --name ros-robot --net=host --privileged \
  -v /dev:/dev -v /home/iot/robot_data:/root/robot_data \
  romindly/ros1-noetic:1.0 \
  bash -c "source /root/ws_romindly/devel/setup.bash && exec roslaunch robot_bringup robot.launch"
ExecStop=/usr/bin/docker stop -t 20 ros-robot
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
```

Note: the two approaches are **mutually exclusive**—if you use systemd, do not also add `--restart=always`, or the two managers will fight each other.

## Data Persistence

The container filesystem is ephemeral (gone after `docker rm`); maps, logs, and rosbags must land on host volumes:

```bash
mkdir -p ~/robot_data/{maps,logs,bags}
docker run ... \
  -v ~/robot_data/maps:/root/robot_data/maps \
  -v ~/robot_data/logs:/root/.ros/log \
  -v ~/robot_data/bags:/root/robot_data/bags \
  romindly/ros1-noetic:1.0
```

This way, maps saved by `map_server`, rosout logs, and black-box rosbags ([Section 04](04_performance_and_ops.md)) are all persisted, and the data stays untouched when switching image versions.

## Multi-Container Orchestration (the One-Liner Version)

Once the system grows, use docker compose to split roscore and the application into two containers (mirroring the dual-service idea of Section 02):

```yaml
services:
  roscore:
    image: romindly/ros1-noetic:1.0
    network_mode: host
    command: roscore
    restart: unless-stopped
  robot:
    image: romindly/ros1-noetic:1.0
    network_mode: host
    privileged: true
    volumes: ["/dev:/dev", "~/robot_data/maps:/root/robot_data/maps"]
    depends_on: [roscore]
    command: bash -c "source /root/ws_romindly/devel/setup.bash && exec roslaunch robot_bringup robot.launch --wait"
    restart: unless-stopped
```

`docker compose up -d` brings everything up in one shot; `--wait` makes the application container wait for roscore to be ready.

## Common Issues

- **`rostopic list` inside the container cannot reach the host master**: you forgot `--net=host`. ROS1 assigns ports randomly, so a port-mapping (-p) approach is not viable; host networking is the only hassle-free solution.
- **rviz reports could not connect to display**: `xhost +local:docker` was not run on the host, or `/tmp/.X11-unix` was not mounted. For remote-ssh scenarios, see the remote operations section of [Section 04](04_performance_and_ops.md).
- **`/dev/rplidar` not visible inside the container**: the symlink is generated by host udev; first confirm the Chapter 45 rules are effective on the host, then confirm you used `-v /dev:/dev --privileged`.
- **`vcs import` is slow or fails during build**: edit `ros1.repos` to switch to mirror prefixes, or build on a development machine with internet access and distribute via save/load—production machines never need to build.
- **Rebuilding the image after every code change is too slow**: during development, use the "mounted source" mode (`-v ~/ws_romindly/src:/root/ws_romindly/src` and rebuild inside the container); only rebuild the image and bump the tag at release time.
